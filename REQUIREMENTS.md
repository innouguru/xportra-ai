# REQUIREMENTS.md — Requirements Source of Truth

> Only requirements already established for the project are recorded here.
> Do not invent detailed functional requirements that have not been approved.
> Every future implementation task must trace to an entry below or an
> approved decision in `docs/decisions/`.

## R-0: Project Foundation (Phase 0) — Established

- R-0.1: The repository shall maintain Markdown documentation as the source
  of truth for project continuity (rather than chat history).
- R-0.2: An agent operating contract shall exist (`AGENTS.md`) defining the
  required read → plan → implement → verify → update-state workflow.
- R-0.3: Current project state shall be tracked in `CURRENT_STATE.md`.
- R-0.4: Exactly one active task shall be tracked in `ACTIVE_TASK.md`, with
  explicit acceptance criteria.
- R-0.5: Approved development phases shall be listed in `ROADMAP.md`
  (Phases 0–10); phases are not implemented until scoped and scheduled.
- R-0.6: Architectural invariants shall be recorded in `INVARIANTS.md` and
  enforced.
- R-0.7: Architectural changes shall require an ADR in `docs/decisions/`.
- R-0.8: Secrets (`.env` values) and the virtual environment (`.venv/`)
  shall never be committed (enforced via `.gitignore`).
- R-0.9: Task lifecycle (`backlog → active → completed/blocked`) shall be
  managed under `tasks/`.
- R-0.10: Test organization (`unit`, `integration`, `regression`,
  `evaluation`, `fixtures`) shall be reserved under `tests/`; no fake tests
  shall be created to fill directories.

## Product Identity (Phase 0.2) — Established

- PI-1: The product name is **Xportra AI**.
- PI-2: Positioning: **AI-powered export compliance intelligence.**
- PI-3: The initial target domain is **Nigerian agricultural exporters**.
- PI-4: Core problem — Xportra AI will help exporters:
  - understand applicable export requirements,
  - organize and interpret compliance evidence,
  - identify compliance gaps, and
  - obtain source-backed regulatory guidance.
- PI-5: Scope boundary — agricultural exports are the initial domain, but
  the underlying system shall not be architected in a way that
  unnecessarily prevents expansion to other export sectors. This is NOT a
  requirement to support other sectors now.

## System Principles (Phase 0.2) — Established

- SP-1 (Deterministic applicability): the system must determine which
  requirements apply using explicit, deterministic business/domain logic.
  An LLM must not be the authoritative mechanism for deciding the
  regulatory universe. (See `docs/decisions/ADR-0001-*.md`.)
- SP-2 (Source-backed intelligence): regulatory guidance generated by the
  system must be grounded in authoritative or explicitly identified
  sources. Source traceability must be preserved.
- SP-3 (Evidence-based compliance): where the system evaluates documents
  or other evidence, conclusions must be traceable to the evidence used.
- SP-4 (Decision support): Xportra AI provides compliance intelligence and
  decision support. It must not silently represent generated guidance as
  legal certification or official regulatory approval.
- SP-5 (Separation of concerns): domain/business rules, retrieval,
  document intelligence, reasoning, persistence, and API/application layers
  shall have clear boundaries. (See
  `docs/architecture/system-boundaries.md`.)
- SP-6 (Production orientation): Xportra AI is intended to become a real
  production system, not a demonstration-only RAG application.

## Non-Goals (Phase 0.2) — Established

- NG-1: Xportra AI is not an official Nigerian government regulatory system.
- NG-2: It does not issue export permits or certificates.
- NG-3: It does not replace competent regulatory authorities.
- NG-4: It does not guarantee regulatory approval.
- NG-5: It does not invent requirements when authoritative information is
  unavailable.
- NG-6: It does not use an LLM as a substitute for deterministic regulatory
  applicability logic.

## Configuration & Dependencies (Phase 0.2) — Strategy Only

- CD-1: The configuration contract in
  `docs/architecture/configuration-contract.md` defines the expected
  configuration categories (variable names only). No provider or production
  infrastructure is selected at this stage.
- CD-2: Variables inherited in `.env` from the previous project are NOT
  Xportra AI requirements. The inherited `.env` is left untouched until a
  canonical schema is approved.
- CD-3: The inherited `.venv` is reused initially to avoid unnecessary
  downloads, but it is NOT the dependency source of truth. Future
  dependencies must be explicitly declared in project dependency
  configuration so the environment can be recreated from the repository.
- CD-4: No dependency file shall be created by snapshotting packages that
  happen to exist in `.venv`. The declaration mechanism is an open
  question (see OQ-4). No packages were installed in this task.

## Configuration & Dependencies (Phase 0.3) — Canonical Schema Established

- CD-5: The canonical environment schema is defined in
  `docs/architecture/environment-schema.md` and is the authoritative
  variable-level specification for Xportra AI.
- CD-6: `.env.example` is the repository-authoritative template for the
  required environment configuration. It contains only safe placeholder
  values and is the approved starting point for local configuration.
- CD-7: `.env` is the local environment file for secrets and machine-
  specific runtime configuration. It must never be committed.
- CD-8: Provider selection remains unresolved; the schema is intentionally
  minimal and provider-neutral and does not approve any production
  infrastructure or vendor-specific configuration.

## Configuration & Dependencies (Phase 0.4) — Python Baseline & Dependency Policy

- CD-9: The project Python baseline is documented in
  `docs/architecture/python-runtime.md` and is set to Python 3.13.x,
  matching the inspected local environment without treating `.venv` as the
  source of truth.
- CD-10: The repository dependency declaration mechanism is `pyproject.toml`.
  It is the authoritative project metadata and dependency configuration file.
- CD-11: The repository configuration is the source of truth for dependency
  declarations; `.venv` is disposable infrastructure and must not be treated
  as a dependency manifest.
- CD-12: Dependencies must be explicitly declared before they become part of
  the project. No package is considered part of Xportra AI merely because it
  exists in the copied local environment.
- CD-13: Direct dependencies, transitive dependencies, and version constraints
  must be tracked explicitly in the repository configuration as the project
  grows.

## Technology Baseline (Phase 0.5) — Approved Initial Stack

- TB-1: The approved initial technology baseline is documented in
  `docs/architecture/technology-baseline.md`.
- TB-2: The core runtime baseline is Python 3.13.x and FastAPI.
- TB-3: The initial storage baseline is PostgreSQL via Supabase Free and
  Supabase Storage Free, with Supabase Auth Free used where authentication is
  required.
- TB-4: The initial vector retrieval baseline is Qdrant running locally
  without Docker.
- TB-5: The initial LLM baseline is OpenRouter with free models.
- TB-6: The initial embedding baseline is sentence-transformers with
  `all-MiniLM-L6-v2`, with the model kept configurable and replaceable.
- TB-7: The ingestion pipeline baseline is Python + `httpx`, PyMuPDF,
  `python-docx`, BeautifulSoup, custom cleaning/normalization, custom
  chunking, sentence-transformers, Qdrant, PostgreSQL, and Supabase Storage.
- TB-8: The initial observability baseline is Python structured logging and
  OpenTelemetry libraries, without a paid observability platform.
- TB-9: The initial development/deployment baseline is Windows with the
  existing Python virtual environment, GitHub, GitHub Actions, and no Docker
  or virtualization-dependent infrastructure currently required.
- TB-10: Xportra AI must remain capable of development and testing using
  free-tier or locally available infrastructure until a specific requirement
  justifies spending money. This is a project principle, not a permanent ban
  on paid infrastructure.
- TB-11: The selected technologies are initial implementations, not
  irreversible architecture commitments; the system should retain reasonable
  abstraction boundaries for replacing providers, models, or infrastructure
  without premature over-engineering.

## Source Authority & Provenance (Phase 0.6) — Approved

- SA-1: Primary legal and regulatory authorities are the preferred source
  tier for Xportra AI guidance.
- SA-2: Official government guidance is explicitly distinguished from law
  or regulation and must not be treated as equivalent without clear
  jurisdictional and legal context.
- SA-3: Recognized international authorities (for example WTO, IPPC, and
  Codex) may be used according to their jurisdictional and technical role,
  but they must not automatically supersede applicable destination-country
  law.
- SA-4: Source status and effective dates shall be tracked separately from
  source authority so superseded or withdrawn guidance does not silently
  remain current.
- SA-5: Lower-tier sources must never be silently treated as equivalent to
  a primary regulatory source.
- SA-6: Origin and destination jurisdictions shall both be represented in
  the architecture for source selection and regulatory applicability.
- SA-7: Source metadata must include authority, jurisdiction, publication
  date, effective date, version, status, source URL, retrieval timestamp,
  supersedes, and superseded_by. This metadata supports source freshness,
  provenance, and supersession tracking without conflating status with
  authority.
